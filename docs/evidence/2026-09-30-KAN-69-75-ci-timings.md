# KAN-69 and KAN-75: observed GitHub CI timings

Recorded on 30 September 2026 from completed GitHub Actions jobs, their step
timestamps, retained logs, coverage artifacts and the workflow/configuration at
each run's commit. All times below are UTC. Durations are seconds, calculated
from GitHub timestamps. This was a read-only census, with no local test run,
benchmark, dependency installation or workflow dispatch.

## Findings and limits

- Five successful pre-sharding frontend jobs and five successful post-sharding
  frontend job groups are available. All 20 shard jobs, including setup and
  artifact upload, finished within the six-minute target. Their maximum duration
  was 263 seconds.
- These are operational before/after observations, not a controlled paired
  benchmark. The before runs were main-branch pushes; the after runs were PR 91
  runs. Source, dependency locks, test counts and workflow structure changed.
  The data does not isolate the causal contribution of sharding.
- Median pre-sharding frontend job duration was 1,038 seconds. Median elapsed
  time from the first frontend job starting to the protected frontend aggregator
  completing was 311 seconds after sharding. Scheduling delays are included in
  the latter figure. Two after workflows were cancelled and one failed outside
  these successful frontend jobs, so this is not evidence of five wholly green
  post-change workflows.
- In the two wholly successful runs in the original after sample, frontend
  completed before the final backend-postgres job. That supports the critical
  path improvement for those observations, not a guarantee for every run.
- The later run at exact PR head `cccfa79f999a4da677991f1906ae478ac8c6e750`
  completed the image path in **69 seconds**, including its protected aggregator,
  or 72 seconds measured from workflow creation. Both dependency lockfiles were
  unchanged from the preceding sampled run and both image builds reused GitHub
  Actions cache entries. This is one observed result below 90 seconds.
- The deliberate uncovered-branch negative PR was not exercised by this census.
  Four weekly Dependabot observations are also not established by this evidence.

## Measurement definitions and resource configuration

`Job duration` is `completed_at - started_at`, including runner setup, execution
and post-job actions. `Start offset` is the job start minus workflow creation;
it includes dependency and scheduling delays, and is not a measured runner queue
metric. `Frontend path` spans the earliest frontend check/shard start through the
protected frontend aggregator completion. `Image path` spans the earliest image
build start through the protected image aggregator completion. Before image
splitting, it is the single images job duration. A run's total duration also
includes other jobs, so it is not interchangeable with either path.

All sampled frontend jobs requested GitHub-hosted `ubuntu-latest`, Node 24 and
pnpm 11. Vitest used `maxWorkers: '50%'`. Physical CPU counts, runner placement,
load and cache warmth were not controlled or independently measured. Before,
one frontend job ran lint, typecheck, tests and build sequentially with jsdom.
After, a separate checks job ran API generation, lint, typecheck, `build:ci` and
the bundle check; four fail-fast-disabled shards ran the Node pure-unit and
jsdom DOM projects. Partial shard coverage thresholds were zeroed for collection;
the merge job retained the global 90% gate. The later auth 95%, global branches
92% and per-file 70% checks were report-only in A1-A3 and enforced in A4-A5.
