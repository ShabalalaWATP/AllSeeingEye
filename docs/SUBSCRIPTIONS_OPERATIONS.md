# Subscription operations (local single-process deployment)

Subscriptions use the existing durable report-job workers. The API lifespan starts the subscription admission loop even when live feeds are disabled. Admission checks for due work every 60 seconds, then saves an edition and a report job. Two local report workers perform generation. A stopped browser does not stop an accepted job.

Each admission tick reads at most 16 overdue schedules and 16 capacity-pending editions. SQL ranks overdue items within each owner, so the first item from every owner is considered before that owner's second. A per-process cursor continues at the next fair-sort key on the following tick and wraps after the final key. Rows that cannot be admitted remain due or pending for a later tick; advancing cadence and reserving the unique edition still occur together in the admission transaction. A process restart resets only the cursor, not the durable due rows, editions or report jobs. The first page after restart is deterministic, then rotation resumes. This is local fairness for the supported single-API-process topology, not a cross-process leader or lease.

This release supports one API process with its database and the existing shared source-control guard. Do not run multiple API scheduler processes against an operator database until leader election, cross-process fairness and recovery have been tested. The repository's SQLite tests exercise local behaviour; the PostgreSQL migration and concurrency acceptance in the implementation plan remain outstanding. Back up and verify the operator database before applying any migration. Do not run test fixtures or `alembic upgrade` against the operator database by accident.

## Observe and diagnose

An administrator with a current session can request `GET /api/admin/subscriptions/diagnostics`. It returns counts and timestamps only: enabled and overdue subscriptions, oldest due lag, active edition workflows, uncertain-outcome and source-failure editions, most recent admitted job, open jobs and queue saturation. Responses are `private, no-store`. It does not test a provider, prove source availability or expose users' questions. A non-administrator cannot use this endpoint. Users can see only their own authorised edition history and monthly usage in Subscriptions.

`source_failure_categories` splits the saved source-failure count by two allowlisted codes: `source_failure_coverage` and `source_disabled`. Each key is present with a zero count when absent. Unknown safe reasons are excluded rather than echoed to an administrator. A saved `scope_revoked` reason can mean source or account authority changed, so it is not labelled as a source failure without stronger evidence. These counts describe retained edition state, not current source health.

If overdue lag rises, check whether the API lifespan is running, whether the admission loop reports a safe `subscription_enqueue_cycle_failed` warning, and whether the global queue is saturated. Review blocked edition reasons in the authorised UI before retrying. An uncertain paid model call is deliberately paused; do not delete and re-create the edition to bypass the preserved reservation. An annual or monthly cadence is anchored to its intended slot, while catch-up coalesces missed slots within the policy rather than issuing a burst of paid reports.

If source failure counts rise, inspect the source's enabled state, configured access and terms, and the edition's coverage. A valid API key alone does not establish a working or permitted source. A report marked Needs review does not become a successful coverage baseline merely because an edition finished. Monthly limits are UTC-calendar accounting ceilings for model requests and output/reasoning tokens, not a guaranteed currency spend cap. Unknown usage holds its reservation across month boundaries.

## Stop and recovery

Graceful application shutdown stops admission and report workers. Saved edition/job state, attempts and reservations survive restart. The worker reuses known completed checkpoints. It does not blindly replay a sent provider call with an unknown outcome. Use the explicit edition controls once its state and usage are understood. Keep a database backup before manual repair, and never change frozen edition dates, brief revisions or evidence in place.

The disposable local acceptance test restarts the feed-disabled API lifespan against the same database. The first start admits one due edition and retained job; shutdown stops the admission loop; the second start observes the same edition without creating another job or due-slot identity. This proves the single-process local restart path only. The PostgreSQL, multi-process and provider-live recovery checks remain separate deployment acceptance work.

An authorised writer can call `POST /api/schedules/{id}/pause` or `POST /api/schedules/{id}/resume` for a personal or team subscription, including one linked to an exact Research Brief revision. Both controls are idempotent and leave the next due slot and frozen definition unchanged. Pause stops new admissions and checkpoint-pauses a queued or running active job in the same database transaction. A provider call already sent may finish and consume usage; its reservation stays retained. Resume re-enables the saved cadence and resumes only a job paused by the schedule control. An edition that was manually paused remains paused and needs its own explicit edition resume. Missed due slots follow the saved catch-up policy on a later admission tick.

In-app edition notification delivery, cross-process deployment, full provider-live checks, user-labelled research quality and browser/export acceptance are tracked in the [implementation plan](RESEARCH_SUBSCRIPTIONS_IMPLEMENTATION_PLAN.md). This guide describes the current local topology and diagnostics, not a production service-level guarantee.
