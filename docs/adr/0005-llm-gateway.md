# ADR 0005: LLM access through a single OpenAI-compatible gateway

Status: Accepted (proposed 2 September 2026, accepted by Alex 3 September 2026)

## Context

Reports must be generated by any OpenAI-compatible endpoint (hosted or local), configured by an admin in the UI. Output must be structured, cited and doctrine-compliant, and all content fed to the model is untrusted.

## Options

1. **The official `openai` Python SDK with a configurable `base_url`**, wrapped in an `LLMGateway` port. Profiles (endpoint, key, model, limits, capabilities such as JSON schema support) are stored encrypted and selected per task role (assessment, fast, embeddings).
2. **LiteLLM** or another multi-provider router. Broader provider support but a large dependency for a need that the OpenAI-compatible convention already covers.
3. **Framework-heavy orchestration** (LangChain, LlamaIndex). Adds abstraction the project does not need and makes prompts harder to audit.

## Decision

Option 1. Prompts are versioned Jinja2 templates in the repository, one per report template, with a shared doctrine preamble. Generation is a pipeline: evidence selection, grading, prompt composition, completion with JSON schema where the profile supports it (otherwise instructed JSON plus repair), validation (schema, citations, yardstick and confidence lint), rendering, persistence. A `FakeLLMGateway` returns canned structured outputs for tests.

## Consequences

- Any endpoint that speaks the OpenAI chat completions API works: Ollama, LM Studio, vLLM, OpenRouter, OpenAI, Groq, Mistral.
- Capability flags per profile (JSON schema, tool calling, context length) decide the prompting strategy and the evidence token budget.
- Token usage and cost are recorded per request for the admin page.
- Model outputs are never trusted: validation failures downgrade a report to `needs_review`.
