# Isolated report PDF renderer

The export use case now awaits an asynchronous renderer and retains the existing exact-version release checks. Existing synchronous PDF/DOCX entrypoints remain available. Default composition uses the existing ReportLab and Word rendering; no browser is installed or enabled automatically. Arabic/Persian language capability flags remain unchanged.

A configured worker receives only the bounded structured ReportDocument projection. Verified Noto Sans Arabic 2.013 regular/bold fonts are embedded into escaped local HTML. The font SHA-256 values are checked at each render; the accompanying OFL licence is packaged. Plain URLs remain inert text. Chromium/PDF extraction and native-speaker acceptance remain separate requirements.

## Ownership and limits

Async exports share immediate two-slot admission. Cancellation of legacy thread rendering waits for the thread before releasing its slot. The browser adapter retains spawn ownership across cancellation, closes the job, reaps the launcher, then removes its private temporary directory. Unverified descendant cleanup disables that worker instance, permanently retains its admission slot and preserves the bounded private input directory for operator recovery. There is no automatic release or deletion without proof of termination. Restarting the app is not itself proof that the old cgroup is empty. Its runtime is cached per container instance, not reconstructed per request.

The optional Linux policy creates only a new `ase-render-*` child under an already delegated cgroup v2 subtree. It requires enabled memory/process controllers, sets a 1 GiB aggregate memory cap, zero swap and 128 processes, then admits the launcher before it starts Bubblewrap. Cleanup writes the owned child's `cgroup.kill`, waits for `populated 0`, and removes that child non-recursively. It never enables parent controllers or modifies host/parent limits. These mechanisms follow the [kernel cgroup v2 documentation](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html).

Bubblewrap receives a dedicated read-only runtime filesystem and new user, PID, network, IPC and UTS namespaces. Both `/work` and `/tmp` are private, explicitly size-limited 64 MiB tmpfs mounts. Only the bounded input HTML is read-only bound from the host. Browser profile and PDF output therefore have no writable host filesystem mount. The fixed `--size` option applies to the following `--tmpfs`, as defined in the [Bubblewrap source](https://github.com/containers/bubblewrap/blob/main/bubblewrap.c). The pinned version must support this option; unsupported versions fail. The environment is cleared. Neither Chromium's sandbox nor network namespace creation has a permissive fallback. Bubblewrap's command line defines the sandbox policy, as explained in its [official documentation](https://github.com/containers/bubblewrap).

The outer work deadline is 60 seconds and the inner browser deadline 45 seconds. Cleanup additionally permits up to five seconds for cgroup emptiness and five seconds to drain/reap launcher output. A failed cleanup quarantines admission instead of declaring termination. PDF output is capped at 16 MiB and 128 pages. PDF parsing and checks for tagged structure run inside the same namespace/cgroup boundary. The child emits a JSON header and PDF through stdout; the parent caps the header at 1 KiB and PDF at 16 MiB, rejects extra output and validates page/byte declarations. Admission requires an explicit true PDF Boolean marker, a structure-root dictionary, nonempty children and parent mapping. These are structural checks, not proof of PDF/UA compliance. HTML remains capped at 8 MiB including fonts.

## Explicit deployment configuration

`ASE_REPORT_PDF_RUNTIME` optionally names an absolute root-owned, non-symlink JSON configuration file. Its six string fields are `rootfs`, `browser`, `browser_sha256`, `bubblewrap`, `bubblewrap_sha256`, and `cgroup_root`. The browser path is absolute inside the isolated filesystem; Bubblewrap and cgroup paths are host paths. Executable hashes pin Chromium and Bubblewrap. Missing files, mismatched hashes, unsupported platforms, failed namespaces or unavailable cgroups fail closed. A configured failure does not silently claim a successful shaped PDF.

The root filesystem must be dedicated, root-owned and non-writable by the application, including its ancestors and contained entries. Escaping symlinks and trees above 20,000 entries are rejected. It must contain Chromium and its libraries, `/usr/bin/python3`, and the matching locked ASE/pypdf installation. Symlinks must resolve within that filesystem. Supply a reproducible pinned runtime image/bundle with its own dependency update and licensing process: executable hash checks do not pin every library. The current backend Dockerfile does not supply this bundle or delegated cgroup tree.

This has material deployment complexity. A root filesystem plus cgroup delegation and working user namespaces is required in addition to the app's ordinary Docker setup. No such infrastructure was created by this change. Runtime construction is operator work; do not weaken isolation with `--no-sandbox`, shared network, writable host mounts or a boolean safety assertion.

## Verification scope

Controlled owned subprocess fixtures test completion, cancellation, deadlines, cancellation during spawn, cleanup failure, slot retention and output validation. Fake policy/job fixtures do not demonstrate kernel isolation. Real generated PDF fixtures test page and tagged-structure admission. Existing PDF/DOCX tests verify compatibility. The focused renderer, projection, export API and final-release group passed 55 tests; no whole-suite or production isolation acceptance is implied.

No actual configured Linux Chromium render, namespace boundary, cgroup OOM, browser sandbox or deployment throughput has been accepted yet. A separate desktop Chrome diagnostic may evaluate the HTML/font projection but cannot establish these properties. Native-speaker review, viewer-specific search/copy, citations/numerals/ZWNJ/marks, pagination and screen-reader/PDF accessibility acceptance remain outstanding. The UTF-8 source companion remains a separate artefact, not a repair to PDF extraction.
