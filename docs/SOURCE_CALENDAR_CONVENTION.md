# Source calendar conversion

Implemented locally on `codex/source-language-date-provenance`. The focused backend acceptance run passed 222 tests. These are the declared conversion conventions and independently published acceptance fixtures, not a claim that the full expansion plan or live-provider acceptance is complete.

`gregorian` accepts explicit ISO dates and timezone-bearing ISO/RFC timestamps. Naive timestamps retain an ambiguous result; invalid or unsupported dates retain their original text. No language, country, digit script or year range selects a calendar. Source dates without a known timezone remain calendar-day intervals with an exclusive next-day endpoint, never artificial UTC publication instants.

`solar_hijri_icu33` names the Unicode ICU 33-year arithmetic Persian convention. The supported input is explicit `YYYY-MM-DD`, with ASCII, Persian or Arabic-Indic digits, restricted to Solar Hijri years 1304 through 1468 inclusive. Original Unicode text is preserved separately from conversion. This is neither the 2820-year arithmetic calendar nor a general Islamic, Afghan, lunar Hijri or astronomical equinox converter.

The mathematical epoch and cycle were checked against [Unicode ICU release 76.1 Persian implementation](https://github.com/unicode-org/icu/blob/release-76-1/icu4c/source/i18n/persncal.cpp). The independently published [ICU PersianTest mapping fixtures](https://github.com/unicode-org/icu/blob/release-76-1/icu4j/main/core/src/test/java/com/ibm/icu/dev/test/calendar/PersianTest.java) include:

| Solar Hijri | Gregorian | Acceptance purpose |
|---|---|---|
| 1304-01-11 | 1925-03-31 | Lower supported year |
| 1374-12-29 | 1996-03-19 | Common year boundary |
| 1375-01-01 | 1996-03-20 | Following new year |
| 1375-12-30 | 1997-03-20 | Leap day |
| 1376-01-01 | 1997-03-21 | Following new year |
| 1384-06-31 | 2005-09-22 | Six-month boundary |
| 1384-07-01 | 2005-09-23 | Thirty-day month boundary |
| 1404-01-01 | 2025-03-21 | Published discriminator against the 2820-year algorithm |
| 1468-12-29 | 2090-03-19 | Upper supported year |

Tests use these constants, not expected dates generated by the implementation being tested. Out-of-range years, invalid month/day combinations, missing calendar and missing timezone have separate regression cases. The pure conversion does not call a network service or add a production dependency. The method identifier `ase-source-date-v1:solar_hijri_icu33` is frozen with each result. Future changes to the convention require a distinct method identifier, never reinterpretation of old frozen metadata.

RSS/Atom modification dates are distinct from publication dates. Ingestion time stays separate. Private declarations target exact owned input and passage/content digests, retain the original input, and create a bounded derived receipt. Declarations and transformations do not overwrite the original passage or citation offsets. Historical evidence, report export and annotation comparison hash paths omit only the newly absent defaults, preserving old canonical bytes.


Dublin Core generic `date` describes an unspecified lifecycle event, so it retains an `unspecified` role and cannot qualify publication recency. Only the exact `http://purl.org/dc/terms/` namespace's `issued` establishes formal issuance. See the primary DCMI definitions for [date](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/terms/date/) and [issued](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/terms/issued/). Unknown namespaces with matching local names retain raw metadata with an unknown calendar, never acquire the DCMI contract by resemblance. These rules apply to new ingestion; existing frozen records are not reinterpreted.
